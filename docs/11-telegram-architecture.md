# 11 — Telegram Architecture (архитектура Telegram)

**Связано:** [07](07-ux-architecture.md) · [08](08-system-architecture.md) · [10](10-api-specification.md) · [12](12-security-plan.md)

Telegram — отдельный **канал продукта**, не единственный интерфейс. Формы с фото и фильтрами остаются на вебе. Mini App — Future.

---

## Роль канала vs бота vs веба

```text
Web (веб-платформа)  ↔  Backend (серверная часть)  ↔  Telegram
        │                         │                      │
   карточки, формы,          статусы, дедуп,         бот DM,
   поиск, админка            подписки, jobs          канал
```

| Сценарий | Telegram | Web |
| --- | --- | --- |
| Login | Widget / oauth данные | Сессия |
| Подписка на типы | Команды или кнопки | Settings (достаточно одного) |
| Новый published | DM по подписке + пост канала | Появляется в поиске |
| Создать кабинет | Нет в MVP | Да |
| Поиск с 4 фильтрами | Нет | Да |
| Пожаловаться | Нет | Да |

## Bot (бот)

### Команды MVP

| Команда | Назначение |
| --- | --- |
| `/start` | Приветствие, привязка если нужно, меню подписок |
| `/settings` | Типы уведомлений |
| `/help` | Что умеет бот + ссылка на сайт |
| `/stop` | Отключить все DM (эквивалент трёх false) |

Не делать в MVP: `/search`, `/create`, `/my-listings`, `/events`, `/spaces` как полноценный UX. Исходник их предлагал — это второй клиент. **Критика:** дублирование форм увеличит баги и модерацию мусора из бота.

Кнопки под `/start`: открыть сайт, кабинеты, события, вакансии (URL), настройка галочек.

### Onboarding (первоначальное знакомство)

Рекомендация DEC-13: Telegram Login на сайте создаёт `TelegramAccount`. Бот узнаёт пользователя по `telegram_user_id`.

```text
Пользователь логинится на сайте
  → User + TelegramAccount
  → онбординг → необязательный opt-in типов (все флаги false по умолчанию)
  → /start подтверждает, что бот может писать
  → настройки на сайте и дубль в боте
```

Если пользователь пришёл в бота раньше сайта: `/start` даёт ссылку Login на сайт с `start` payload. Не собирать профиль в чате.

### Profile / search / create listing

Не в боте. Сообщения-заглушки: «Создать объявление можно на сайте: URL».

### Notifications (уведомления) в боте

Текст-шаблон (не маркетинг):

```text
Новое объявление: {title}
Тип: кабинет | событие | вакансия
Район: {district}
{price or date}
{url}
```

Один listing — одно DM на пользователя (дедуп).

### Settings

Инлайн: 🏠 кабинеты вкл/выкл, 📅 события, 💼 вакансии.

## Channel (канал)

Имя рабочее: «Beauty Hub Ростов» (`ASSUMPTION`).

**Что попадает:** только `published` карточки, краткая карточка + ссылка. Не репосты чатов, не уроки, не реклама бренда в MVP (ручной пост админа в канале возможен операционно, не как API).

**Что не попадает:** draft, pending, rejected, expired (новые посты). Старые посты канала не редактируем обязательно (`ASSUMPTION`).

Модерация канала: бот с правами пост; человеческий admin как backup.

---

## Notification System (система уведомлений)

```text
New Listing (новое объявление) status=published
 ↓
Matching Engine (механизм подбора)
  MVP: фильтр по NotificationPreference.type
  P1: Search Intent rules
 ↓
Eligible Users (подходящие пользователи)
  не автор объявления
  bot_blocked = false
  opt-in соответствующего типа
 ↓
Notification Queue (очередь уведомлений)
  запись Notification pending + dedup_key
 ↓
Telegram sendMessage
 ↓
sent | failed → retry
```

Параллельно: один channel post, отдельный Notification без user_id.

**Смягчение шума:** opt-in, все флаги по умолчанию false (DEC-12). Не default-all-on.

## Webhook (веб-перехватчик)

- HTTPS endpoint из [10](10-api-specification.md)
- Секрет `secret_token`
- Ответ 200 быстро; тяжёлая логика — после
- Дедуп `update_id`

---

## Retries (повторные попытки)

- Telegram 429: уважать `retry_after`
- 5xx: экспоненциальный backoff, 3–5 попыток
- 403 bot blocked: `bot_blocked=true`, не ретраить DM
- После исчерпания: status failed, алерт если доля failures > порога TBD

---

## Rate limits (ограничения частоты)

Соблюдать лимиты Bot API (группы/DM). При многих подписчиках — не слать в цикле на approve request: job батчами. На старте (десятки пользователей) синхронный цикл допустим; условие пересмотра — таймаут approve.

Канал: 1 пост на listing.

---

## Idempotency (идемпотентность)

`dedup_key` unique. Повтор job не создаёт второй send.

Webhook `/start` повторный не плодит User.

---

## Failures (сбои)

Сайт не зависит от успешности send (NFR-10). Админ видит failed в логах. Пользователь не получает «тихо ничего» на сайте.

---

## Unsubscribe (отписка)

`/stop`, снятие галочек, Block бота (403). Не слать после block. Канал: пользователь отписывается нативно в Telegram — мы не контролируем.

---

## Notification preferences (настройки уведомлений)

Источник правды: таблица NotificationPreference и сайт `/settings` (DEC-16). Бот дублирует три переключателя.

---

## Безопасность (кратко)

Полный разбор: [12](12-security-plan.md). Webhook secret, не логировать token, не выполнять произвольный текст пользователя как команду с SQL, лимиты на `/start` abuse.

---

## Критика «Telegram как единственный интерфейс»

Гипотеза «мастера не откроют сайт» не подтверждена. Если сделать только бота, поиск и модерация фото деградируют. Решение пакета: **обязательный веб + опциональный бот**. Если бета покажет 90% только канал без логина — усилить канал, не выкидывать веб как систему записи.
