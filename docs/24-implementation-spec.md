## 0. Зачем этот документ

Пакет 00–23 описал продукт, но оставил `DECISION REQUIRED` и внутренние расхождения (порядок Admin vs Telegram, роли салона/помещения, opt-in, контакт, навигация). Дизайнер и разработчик не могут работать по «рекомендациям».

Этот файл:

1. закрывает решения, нужные для макетов и MVP;
2. фиксирует **замороженный MVP**;
3. даёт UX/UI-спецификацию экранов, состояний и копирайта;
4. задаёт последовательность: дизайн → реализация → бета.

Что **не** заморожено здесь (не блокирует UX): юридическое лицо и тексты 152-ФЗ (D-02), конкретный вендор хостинга, ФИО модератора.

## 2. Замороженный MVP (канон)

### 2.1. One-liner

Beauty Hub — профессиональная инфраструктура beauty-индустрии Ростова: структурированные объявления кабинетов, мероприятий и вакансий на сайте и доставка по типу в Telegram.

### 2.2. Гипотеза, которую проверяет MVP

Структурированные карточки трёх типов + вход через Telegram + уведомления по **включённому типу** дают соединения (прокси: `contact_clicked`) лучше, чем чат или одна только доска Avito.

Matching, Radar, Club, каталог мастеров, Mini App — **не MVP**.

### 2.3. P0 — входит в первый программный релиз беты

| ID | Функция | Готово когда |
| --- | --- | --- |
| MVP-01 | Telegram Login + сессия + выход | CUJ-1 |
| MVP-02 | Онбординг: роль, имя, контакт Telegram | CUJ-2, `profile_completed` |
| MVP-03 | Справочники: специализации, районы | фильтры работают |
| MVP-04 | CRUD объявлений трёх типов + фото + draft/pending | CUJ-3 |
| MVP-05 | Админка: очередь, approve/reject, block user | CUJ-10 |
| MVP-06 | Жалобы | CUJ-9 |
| MVP-07 | Публичные списки, фильтры, карточка | CUJ-4, CUJ-5 |
| MVP-08 | Контакт после входа | CUJ-6 |
| MVP-09 | Истечение статусов (job) | US-L-04 |
| MVP-10 | Telegram: канал + DM по opt-in типу + /start /settings /stop | CUJ-7 |
| MVP-11 | События аналитики P0 | [14](14-analytics.md) |
| MVP-12 | Empty / loading / error на списках и формах | [07](07-ux-architecture.md) |
| MVP-13 | Страницы legal (контент может быть плейсхолдером до DEC-02) | маршруты есть |
| MVP-14 | Удаление аккаунта | BH-FR-23 |

### 2.4. Явно не входит (Won't / P1+)

Обучение, лента, мессенджер, Mini App, мобильные приложения, оплата, AI, Elasticsearch, микросервисы, Kubernetes, Match scoring, Search Intent, избранное, Radar, каталог людей, кабинет бренда, phone auth, внутренние билеты Event.

### 2.5. Роли и права

| role | Подпись в UI | Дефолт Create | Может |
| --- | --- | --- | --- |
| `master` | Мастер | не выбран (сначала поиск) | всё в §2.3 как пользователь |
| `space_owner` | Салон или помещение | Кабинет | Space, Vacancy, Event |
| `organizer` | Организатор | Мероприятие | Space, Vacancy, Event |
| `admin` | не в онбординге | — | модерация; задаётся вручную в БД |

Гость: читать published, без контакта, без Create (Create → Login).

### 2.6. Статусы Listing

`draft` → `pending` → `published` \| `rejected`  
`published` → `expired` \| `archived`  
`published` + edit → `pending`

Публичный GET — только `published` и не expired.

## 3. UX/UI Specification (для дизайнера)

Цель дизайна: **mobile-first**, мало шагов, профессионально спокойно (не «бьюти-гламур ради ленты», не маркетплейс-крик). Не соцсеть: нет лайков, сторис, аватарок в ленте как feed.

### 3.1. Принципы интерфейса

1. Сначала польза (карточка: район, цена/дата, специализация), потом декорации.
2. Один главный CTA на экран.
3. Пустое состояние предлагает действие (сбросить фильтр / открыть Telegram / создать).
4. Не имитировать активность.
5. Контакт не светить гостю.
6. Русский язык. Типы в UI: «Кабинет», «Мероприятие», «Вакансия».

### 3.2. Брейкпоинты

| Имя | Ширина | Навигация |
| --- | --- | --- |
| mobile | 375–767 | нижний таббар 4 пункта |
| tablet | 768–1023 | таббар или верх, на усмотрение, карточки 2 колонки |
| desktop | ≥1024 | верхнее меню, список+фильтры слева или сверху |

Масштабы макетов обязательны: **375** и **1280**. 768 — желательно.

### 3.3. Токены (семантика, не CSS)

Дизайнер задаёт в Figma variables:

- `color.bg`, `color.surface`, `color.text`, `color.textMuted`, `color.accent`, `color.accentText`
- `color.success` / `warning` / `danger` (статусы pending/rejected)
- `color.border`
- Типографика: заголовок экрана, заголовок карточки, цена, мета (район), body, подпись кнопки
- Радиус карточки, отступ сетки 8pt
- Тень карточки — слабая или без

Не использовать стоковые «салонные» розовые градиенты как идентичность, пока нет брендбука. Нейтральная база + один accent.

Референс стека реализации (`ASSUMPTION`): Tailwind; визуал макетов первичен.

### 3.4. Навигация (заморожена)

**Mobile tabbar:**

1. Главная — `/`
2. Поиск — `/search` (чип типа по умолчанию: Кабинеты)
3. Создать — `/create` (гость → `/login?next=/create`)
4. Профиль — `/profile` (гость → `/login`)

**Desktop header:** логотип, Кабинеты, События, Вакансии, Создать, Профиль / Войти.

Нет: Masters, Уведомления inbox, вкладка Telegram.

### 3.6. Компоненты (дизайн-система продукта)

Сдать как variants:

- `AppHeader` / `TabBar`
- `ListingCard` (space / event / vacancy): фото, тип-бейдж, заголовок, район, цена или дата, специализации (1–2 чипа +N)
- `StatusBadge`: pending, published, rejected, expired, archived
- `FilterSheet` (mobile) / `FilterBar` (desktop): район, специализация, цена, дата
- `TypeChips`: Кабинеты / Мероприятия / Вакансии
- `Button` primary / secondary / danger
- `Input`, `Textarea`, `Select`, `Checkbox`, `Toggle`
- `FileUploader` (фото, прогресс, ошибка типа/размера)
- `EmptyState` (иконка простая, текст, 1–2 CTA)
- `SkeletonCard`
- `ErrorBanner` + Retry
- `ContactButton` (гость: «Войти, чтобы написать»; авторизован: «Написать в Telegram» / «Позвонить» если phone)
- `ModerationBanner` у автора на своей карточке

Не делать: stories, like, share-to-feed, чат-виджет.

### 3.7. Поля форм (точно)

**Онбординг профиля (обязательные *):**

- Роль *
- Имя *
- Telegram @ или номер для связи * (если Login дал username — предзаполнить, можно править)
- Район (мастер — желательно; не блокер `profile_completed`)
- Специализация * только для `master`
- Телефон, Instagram, фото, «о себе» — опционально

`profile_completed` = роль + имя + contact_telegram.

**Space:** заголовок*, описание*, район*, специализации* (мульти, ≥1), цена* число, период* месяц/смена/час, площадь м² опц., вид места опц. (кабинет / кресло / коворкинг / другое), фото ≥1*, контакт (по умолчанию с профиля).

**Event:** заголовок*, описание*, starts_at*, район*, адрес текстом опц., специализации*, цена или «бесплатно»*, capacity опц., external_url опц., фото опц. (≥0).

**Vacancy:** заголовок*, описание*, район*, специализация* (одна или мульти — **заморожено: мульти как у Space**), `direction`*: ищу мастера / ищу работу, формат занятости: аренда / найм / процент / другое (select), фото опц.

### 3.8. Фильтры поиска

Всегда: тип (чипы).  
Общие: район, специализация.  
Space: цена от–до.  
Event: дата от (и опционально до).  
Vacancy: direction.

Сортировка только «сначала новые». Нет карты.

### 3.10. Ключевые потоки для прототипа (кликабельно)

**P-1 Гость ищет кабинет:** Home → Поиск (чип Кабинеты) → фильтр район → карточка → CTA Войти → Login → возврат на карточку → Показать контакт.

**P-2 Создание кабинета:** Профиль completed → Создать → Кабинет → форма → превью → отправка → Pending OK.

**P-3 Модерация:** Admin queue → карточка → Approve → в поиске гостя появляется.

**P-4 Telegram:** Settings тоггл Мероприятия вкл → (в прототипе — annotation) DM со ссылкой на карточку.

Не прототипировать Matching.

### 3.11. Telegram (макеты сообщений)

Дизайнер отдаёт 3 текстовых каркаса + разметку кнопок (не UI-кит Telegram):

**DM:**

```text
Новое объявление · {Кабинет|Мероприятие|Вакансия}
{title}
{district} · {price или date}
Открыть карточку
```

Кнопка URL: `{site}/listings/{id}?utm_source=telegram&utm_medium=dm`

**Канал:** то же + «Beauty Hub Ростов».  
**Устарело:** если карточка expired — сайт показывает SCR-CARD expired; бот не обязан редактировать пост.

### 3.12. Админка UX

Не публичный бренд. Утилитарно: таблица pending, превью фото, кнопки Одобрить / Отклонить (поле причины обязано при reject). Не проектировать «красивый CMS».

### 3.13. Доступность (минимум)

Контраст текста, 44px зоны таббара, focus на desktop, alt у фото («фото кабинета» если нет подписи), не полагаться только на цвет бейджа.

## 8. Последовательность разработки

Полные зависимости: [21](21-dependency-map.md). Этапы ниже **заменяют** порядок «Этап 6 Admin после Telegram» из старого §11 в [00](00-project-blueprint.md).

Длительность не обещать. Этапы относительные.

```text
U0  UX/UI (макеты §3)          ← стартовать сразу
 │
 ├─ параллельно  D0 Discovery + seed   ← операционный трек
 │
 E1  Foundation (репо, CI, БД, storage, staging)
 E2  Auth + профили + справочники
 E3  Listings + медиа + статусы
 E4  Admin + жалобы + approve     ← до Telegram
 E5  Search + фильтры + контакт + empty states
 E6  Telegram канал + opt-in DM
 E7  Legal placeholders, expire job, аналитика, hardening
 E8  Закрытая бета (гейт: seed + модератор + DEC-02)
 E9  Matching v1 только по сигналу беты
```

### Правила параллелизма

- U0 не ждёт интервью.
- E1 можно начинать, когда есть этот файл; UI-верстку экрана не считать Done без макета этого экрана (или явного «верстать по §3 без Figma» от Product).
- E4 обязан быть до E6.
- E8 не начинать без операционного seed.
- E9 запрещён в том же релизе, что E1–E7.

### U0 — UX/UI (первый практический шаг)

1. Токены и карточка ListingCard.  
2. Search + Card + Login (P-1).  
3. Create Space (P-2).  
4. Остальные Create, Profile, Settings.  
5. Admin утилитарно.  
6. Тексты Telegram.  
7. Прототип P-1…P-3, ревью Product.

**Выход U0:** DoD §3.14.  
**Вход в вёрстку E2+:** макеты Login/Onboarding; в E3 — Create; в E5 — Search/Card.

### E1…E9

Соответствуют Sprint 1–8 в [22](22-execution-order.md) с поправкой: нумерация E4 = Admin, E6 = Telegram. Backlog ID BH-001…034 — [20](20-roadmap-backlog.md).
