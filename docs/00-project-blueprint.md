## Как читать статусы уверенности

| Метка | Значение |
| --- | --- |
| `VALIDATED` | Подтверждено исходным текстом заказчика или наблюдаемым фактом (не интервью). |
| `HYPOTHESIS` | Рабочая гипотеза: есть способ проверки, нет доказательства. |

## One-liner (одно предложение)

Beauty Hub — профессиональная инфраструктура beauty-индустрии Ростова, где мастера, салоны, владельцы кабинетов и организаторы находят друг друга через структурированные объявления и Telegram, а не через хаос чатов.

## Elevator Pitch (краткая презентация)

В Ростове информация для мастеров размазана по Avito, Instagram, VK и Telegram-чатам: кабинет тонет в ленте, мастер-класс не доходит до нужной специализации, салон не знает, где искать арендатора. Beauty Hub хранит объявления в структурированном виде на веб-платформе и доставляет подходящие типы предложений в Telegram. Платформа не учит профессии, не заменяет соцсеть и не копирует доску объявлений: она соединяет спрос и предложение внутри одной городской индустрии.

Статус формулировки: `HYPOTHESIS` (гипотеза позиционирования; ценность не подтверждена рынком).

## 1. Discovery Summary (итог исследования и анализа)

### 1.1. Какую проблему решаем

**Проблема (формулировка):** у участников beauty-индустрии города нет единого профессионального информационного слоя. Нужная информация существует, но её нельзя надёжно найти, отфильтровать и получить вовремя.

Конкретные боли из исходника (`VALIDATED` как заявленные заказчиком, не как измеренные):

| Сторона | Боль |
| --- | --- |
| Организатор / барбер | Непонятно, как пригласить именно мастеров на мастер-класс. |
| Владелец помещения | Есть свободный кабинет — неясно, как быстро сообщить мастерам. |
| Мастер | Неясно, где сейчас свободное помещение / рабочее место. |
| Индустрия в целом | Нет места, где собраны мастер-классы, помещения и смежная профессиональная информация — без обучения. |

### 1.2. Для кого

| Роль | Роль в MVP | Статус |
| --- | --- | --- |
| Beauty Master (мастер) | Primary (основной пользователь спроса) | `HYPOTHESIS` |
| Space Owner (владелец помещения / салона) | Primary supply (кабинеты и вакансии). В реализации одна роль `space_owner` | `HYPOTHESIS` |
| Event Organizer (организатор) | Primary supply мероприятий | `HYPOTHESIS` |
| Brand / Supplier (бренд / поставщик) | Не кабинет MVP; канал роста и будущая монетизация | `ASSUMPTION` |

Персоны не подтверждены интервью. План валидации: [03 — Personas & JTBD](03-personas-jtbd.md).

### 1.3. Почему существующие решения неудобны

Наблюдаемые свойства (не полнота рынка):

- **Avito:** структурированные объявления аренды кабинетов в Ростове уже есть. Слабое место для нашей гипотезы — это не профессиональная среда мастеров, не события, не Telegram-доставка по типу, смешение с потребительским спросом. `RESEARCH REQUIRED`: доля мастеров, которые реально ищут кабинет на Avito.
- **Telegram-чаты:** удобный канал, плохая память. Объявление тонет. Нет фильтров, категорий, срока жизни, поиска. Исходник утверждает «группы по ~30 человек и нет активности» — это **не измерено**. Публично существуют каналы разного размера, часть из них ориентирована на клиентов и моделей, не на B2B-мастеров. `RESEARCH REQUIRED`.
- **Instagram / VK:** лента и сторис, нет надёжного поиска кабинета по району и специализации.
- **Бьюти-коворкинги:** закрывают аренду конкретного пространства, не рынок города и не события.

Подробнее: [02 — Market Research](02-market-research.md).

### 1.4. Ключевые Jobs To Be Done (задачи пользователя)

**Primary JTBD (основные):**

1. Когда мне нужен кабинет, я хочу быстро увидеть актуальные варианты в своём районе и специализации.
2. Когда у меня освободилось место, я хочу сообщить мастерам города, не публикуя одно и то же в десяти чатах.
3. Когда я провожу мастер-класс, я хочу дойти до мастеров нужного направления до того, как места закончатся.
4. Когда в городе появляется релевантное предложение, я хочу узнать об этом в Telegram, а не случайно наткнуться в ленте.

Полный набор: [03 — Personas & JTBD](03-personas-jtbd.md).

### 1.5. Продуктовая гипотеза

> Если в Ростове собрать структурированные объявления типов Space (помещение), Event (мероприятие) и Vacancy (вакансия) и доставлять их мастерам в Telegram по подписке на тип, мастера начнут возвращаться, а владельцы помещений и организаторы получат отклики быстрее, чем через чат или Avito.

Статус: `HYPOTHESIS`.  
Проверка: закрытая бета, метрики `listing_created`, `listing_viewed`, `contact_clicked`, ручной follow-up успешных соединений. См. [14 — Analytics](14-analytics.md) и [18 — Metrics](18-metrics.md).

### 1.6. Главные риски

1. Chicken-and-egg (проблема курицы и яйца): нет объявлений → нет мастеров, и наоборот.
2. Продукт неотличим от Avito для сценария аренды кабинета.
3. Telegram-канал превращается в тот же шум, что и чаты, если нет модерации и подписок по типу.
4. Matching (подбор) слишком рано → разработка без ценности.
5. Scope creep (разрастание объёма): Club, Radar, мессенджер, каталог мастеров как соцсеть.

Реестр: [19 — Risk Register](19-risk-register.md).

### 1.7. Главные assumptions (предположения)

| ID | Предположение | Статус |
| --- | --- | --- |
| A-01 | Мастера Ростова ежедневно пользуются Telegram. | `ASSUMPTION` — высокая правдоподобность, не измерено |
| A-02 | Владельцы кабинетов готовы бесплатно отдать объявления на новую площадку. | `HYPOTHESIS` |
| A-03 | Плотность в одном городе важнее федеральной «тонкой» аудитории. | `ASSUMPTION` из стратегии local-first |
| A-04 | Контакт вне платформы (Telegram / телефон) достаточен для MVP. | `ASSUMPTION` |
| A-05 | Команда небольшая; modular monolith (модульный монолит) уместен. | `ASSUMPTION` |
| A-06 | Стек Next.js + TypeScript + PostgreSQL. | `ASSUMPTION` (репозиторий пуст) |

### 1.8. Что проверить до разработки

1. 15–20 интервью (минимум 8 до **закрытой беты**; UX не ждут): последний поиск кабинета / мероприятия, канал, время, причина отказа от чата.
2. Карта Telegram / VK / Avito: размер, активность, мастер vs клиент.
3. Seed (наполнение): договорённость о 15–30 реальных объявлениях на старт беты.
4. Правовая рамка ПДн и публичных контактов. `DECISION REQUIRED`.

**Стоп-условие для закрытой беты:** нет (а) 8+ интервью с подтверждённой болью и (б) 15–30 обещанных объявлений — **не открывать бету**.  
**UX/UI и Foundation кода** можно начинать по [24](24-implementation-spec.md) (DEC-17): макеты не ждут интервью; публичная проверка гипотезы без seed по-прежнему бессмысленна.

### 1.9. Что является MVP

См. [05 — MVP Scope](05-mvp-scope.md). Кратко P0:

- Веб: роли `master` / `space_owner` / `organizer`, короткий профиль, объявления Space / Event / Vacancy, поиск и фильтры, контакт после входа, жалобы.
- Telegram: канал модерированных публикаций + бот (привязка, подписка на **типы** объявлений, deep link на карточку сайта).
- Админка и модерация статусов.
- Аналитика событий с первого дня.

Matching (подбор по Search Intent и scoring) — **не MVP**. Решение: после закрытой беты (`P1`). Подтверждено при планировании.

### 1.10. Future Scope (будущий объём)

- Beauty Match v1: Search Intent + rule-based scoring.
- Radar-lite на главной и ежедневный дайджест — после плотности объявлений.
- Каталог мастеров, коллаборации, поиск модели — только если интервью подтвердят спрос и это не превратит продукт в соцсеть.
- Beauty Club, meetup, скидки партнёров — операционный рост, не ядро продукта.
- Монетизация: продвижение объявления, платное событие, B2B для брендов.
- Георасширение: другие города.
- Redis / очередь воркеров / вынос API — по сигналу нагрузки.

### 1.11. Слабые и противоречивые места исходника

| Место | Критика | Решение в этом пакете |
| --- | --- | --- |
| Оценки «шанс 8/10», «интерес 10/10» | Нет данных | Не переносить |
| Telegram-бот как полный UX + Mini App + сайт | Три продукта | Сайт = система записи; бот = уведомления и канал |
| Match как «главная фишка» сразу | Без supply бесполезен | После беты |
| Trust: отзывы и верификация в принципах, но не в MVP | Противоречие | MVP: модерация + жалобы; верификация — Future |
| Listing типа Master vs каталог людей | Риск соцсети | В MVP нет каталога мастеров как сущности поиска «людей» |
| «Группы по 30 человек» | Не измерено | `RESEARCH REQUIRED` |
| Числовые цели seed 100–200 объектов | Нет основания | Качественный seed, числа TBD |

## 2. Как работает продукт

```text
Спрос (мастер)                    Предложение
      │                           (салон / помещение / организатор)
      │                                      │
      ▼                                      ▼
Поиск / подписка на тип          Создание объявления
      │                                      │
      └──────────────┬───────────────────────┘
                     ▼
              Веб-платформа
           (карточки, фильтры,
            статусы, модерация)
                     │
                     ▼
                 Telegram
        канал + уведомления по типу
                     │
                     ▼
            Контакт вне платформы
          (Telegram / телефон)
                     │
                     ▼
         Successful Connection
         (успешное соединение)
```

После беты добавляется Matching Engine (механизм подбора) между новым объявлением и Search Intent (поисковым намерением).

## 4. Архитектура (кратко)

**Решение:** Modular Monolith (модульный монолит). Не микросервисы.

```text
Пользователь
    │
    ├── Веб (Next.js)
    └── Telegram (Bot API + канал)
            │
            ▼
     Application (модульный монолит)
       Auth | Profiles | Listings | Search
       Notifications | Telegram | Moderation | Admin
            │
            ├── PostgreSQL
            └── Object Storage (фото)
```

- Поиск MVP: PostgreSQL + индексы.
- Redis / очереди: Stage 2, если уведомления начнут задерживаться.
- Детали: [08 — System Architecture](08-system-architecture.md), ADR в том же файле.

## 5. Технологии (`ASSUMPTION`)

| Слой | Выбор | Зачем MVP | Когда пересмотреть |
| --- | --- | --- | --- |
| Frontend / Backend | Next.js + TypeScript | Один репозиторий, мало команды | Нагрузка или отдельная команда API |
| UI | Tailwind + существующая компонентная библиотека | Скорость | Не критично |
| БД | PostgreSQL | Объявления, поиск, транзакции | — |
| Файлы | S3-совместимое хранилище | Фото профилей и объявлений | — |
| Telegram | Bot API, webhook | Уведомления и канал | Сбой Bot API → веб остаётся |
| Аналитика | События в БД + простой экспорт / PostHog | Понять, работает ли продукт | — |
| Хостинг | Один инстанс + managed PostgreSQL; вендор в Foundation (DEC-01) | Простота | Рост трафика |

Не использовать без обоснования: Kubernetes, Kafka, Elasticsearch, микросервисы, LLM.

## 6. Telegram

Telegram — слой дистрибуции и уведомлений, не единственный интерфейс.

| Сценарий | Где выполняется |
| --- | --- |
| Привязать аккаунт, выбрать типы подписки | Бот |
| Получить карточку нового объявления | Бот / канал |
| Создать кабинет / мероприятие с полями и фото | Веб |
| Поиск с несколькими фильтрами | Веб |
| Пожаловаться, модерировать | Веб / админка |

Deep link из Telegram всегда ведёт на карточку сайта (или на ту же карточку через авторизованную сессию).

Подробнее: [11 — Telegram Architecture](11-telegram-architecture.md).

## 7. Matching (подбор)

**Не входит в MVP.**

Matching v1 (после беты, при наличии объявлений и возвратов):

1. Пользователь сохраняет Search Intent («ищу кабинет, nail, Ворошиловский, до 20 000 ₽»).
2. Новое опубликованное объявление проходит rule-based фильтр.
3. Совпадения ставятся в очередь уведомлений Telegram.

Scoring «подходит на 94%» и механика Tinder — не делать, пока простые правила не докажут ценность. См. ADR-004 в [08](08-system-architecture.md).

## 9. Метрики

Guardrail (защитные): жалобы, отписки от бота, частота уведомлений.

## 12. Подтверждённые решения / гипотезы / открытые вопросы

### Подтверждённые решения (внутри этого пакета, не рынком)

- Первый город: Ростов-на-Дону. `VALIDATED` из исходника.
- Не школа, не соцсеть, не копия Avito. `VALIDATED` как ограничение заказчика.
- Matching после беты. `VALIDATED` как решение планирования.
- Modular monolith, PostgreSQL, без Kubernetes. Решение масштаба MVP.
- Telegram = дистрибуция; веб = система записи.

### Рабочие гипотезы

- Структурированные объявления + Telegram по типу бьют чат и Avito по сценариям событий и «кабинет для мастера».
- North Star = успешные соединения.
- Telegram Login как единственный auth MVP (DEC-04, заморожено).

### Открытые вопросы

Закрыты для UX/MVP в [24](24-implementation-spec.md): D-03, D-04, D-06, порядок Admin, роли, opt-in, навигация.

| ID | Вопрос | Статус |
| --- | --- | --- |
| D-01 | Конкретный вендор хостинга | Открыт; DEC-01 задаёт рамку. Блокер деплоя, не макетов |
| D-02 | Юридическое лицо, оферта, 152-ФЗ | Открыт. Блокер прод-регистрации. Макеты — плейсхолдеры |
| D-05 имя | Кто именно модерирует | Открыт. SLA в UI: 24 часа (DEC-05). Блокер беты |

### Требует исследования

- Реальный размер и активность локальных Telegram/VK-сообществ.
- Как мастера сейчас находят кабинеты (Avito vs сарафан vs чаты).
- Спрос на «ищу модель» и коллаборации vs три типа P0.
- Готовность организаторов отдавать события бесплатно.

## 13. Глоссарий

| Термин | Русский смысл |
| --- | --- |
| Listing | Объявление; в MVP типы: `space`, `event`, `vacancy` |
| Space | Помещение / кабинет / рабочее место |
| Event | Мероприятие, в первую очередь мастер-класс |
| Vacancy | Вакансия / «ищу мастера» |
| Search Intent | Сохранённое поисковое намерение (после беты) |
| Match | Совпадение объявления и намерения |
| Successful Connection | Подтверждённое соединение сторон (не просто просмотр) |
| Seed | Ручное наполнение предложения до запуска |
| Modular monolith | Одно приложение с внутренними доменными модулями |
| Telegram-first | Сначала привычный канал доставки, не «только бот» |

Единые идентификаторы требований: `BH-FR-*` в [04 — PRD](04-prd.md). Истории: `US-*` в [06 — User Stories](06-user-stories.md).
